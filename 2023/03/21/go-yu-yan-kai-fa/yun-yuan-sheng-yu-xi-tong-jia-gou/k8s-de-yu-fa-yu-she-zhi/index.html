1 Kubectl命令行工具

  kubectl 是使用 Kubernetes API 与 Kubernetes 集群的控制面进行通信的命令行工具。

apiVersion: v1
kind: Pod
metadata:
  name: my-pod  # 指定 Pod 的名称
spec:
  containers:
    - name: nginx-container
      image: nginx:latest

1.1 Kubectl使用格式

  Kubectl提供了多种子命令和参数，帮助用户执行各种操作，比如创建、更新、删除资源，以及查看集群状态等。使用格式如下：

kubectl [command] [TYPE] [NAME] [flags]

  1.command：指定要对一个或多个资源执行的操作，如create(创建)、get(获取)、describe(描述)和delete(删除)等。

  2.TYPE：指定资源类型。资源类型不区分大小写，并且可以以单数、复数或简写形式表示。以下命令输出相同的结果：

kubectl get pod mypod
kubectl get pods mypod
kubectl get po mypod

  以上三种形式等效，均用于获取名为mypod的Pod信息。

  注明：资源类型使用使用kubectl api-resources来查询。

  3.NAME：指定资源的名称，区分大小写。如果省略名称，则显示虽所有资源的详细信息。kabectl get pods返回所有Pod的列表。对多个资源执行操作时，可以按类型和名称指定每个资源，或指定一个或多个文件。

   1.按类型和名称指定资源：

   对所有类型相同的资源进行分组：TYPE1 name1 name2 name<#>。kubectl get pod example-pod1 example-pod2

   2.指定多个资源类型：

   TYPE1/name1 TYPE1/name2 TYPE2/name3 TYPE<#>/name<#>。kubectl get pod/example-pod1 replicationcontroller/example-rc1

   3.用一个或多个文件指定资源：-f file1 -f file2 -f file<#>

   使用 YAML 而不是 JSON， 因为 YAML 对用户更友好, 特别是对于配置文件。 例子：kubectl get -f ./pod.yaml。

  4.flags部分：Kubectl子命令的可选参数。

  使用-s或–server参数指定Kubernetes API服务器的地址和端口。

  注明：

   1.从命令行指定的参数会覆盖默认值和任何相应的环境变量。

   2.如果需要帮助，在终端窗口中运行 kubectl help。

   3.使用kubectl create -h 获得子命令帮助。

1.4 格式化输出

  以特定格式在终端窗口输出详细信息， 可以将 -o 或 --output 参数添加到受支持的 kubectl 命令中。

# 语法
kubectl [command] [TYPE] [NAME] -o <output_format>

  具体的 kubectl 操作，支持的输出格式如下：

输出格式 描述
-o custom-columns= 使用逗号分隔的自定义列列表打印表。
-o custom-columns-file= 使用 <filename> 文件中的自定义列模板打印表。
-o json 输出 JSON 格式的 API 对象
`-o jsonpath= 打印 jsonpath 表达式定义的字段
-o jsonpath-file= 打印 <filename> 文件中 jsonpath 表达式定义的字段。
-o name 仅打印资源名称而不打印任何其他内容。
-o wide 以纯文本格式输出，包含所有附加信息。对于 Pod 包含节点名。
-o yaml 输出 YAML 格式的 API 对象。 
# 将单个 Pod 的详细信息输出为 YAML 格式的对象
kubectl get pod web-pod-13je7 -o yaml

1.5 自定义列

  定义自定义列并仅将所需的详细信息输出到表中，可以使用 custom-columns 选项。

  选择内联定义自定义列或使用模板文件：-o custom-columns= 或 -o custom-columns-file=。

1.内联
  kubectl get pods <pod-name> -o custom-columns=NAME:.metadata.name,RSRC:.metadata.resourceVersion

2.模板文件
  kubectl get pods <pod-name> -o custom-columns-file=template.txt
  `template.txt` 文件包含：
  NAME          RSRC
  metadata.name metadata.resourceVersion

1.6 Server-side 列

  kubectl 支持从服务器接收关于对象的特定列信息。 意味着对于任何给定的资源，服务器将返回与该资源相关的列和行，以便客户端打印。 通过让服务器封装打印的细节，这允许在针对同一集群使用的客户端之间提供一致的人类可读输出。

  此功能默认启用。要禁用它，请将该 --server-print=false 参数添加到 kubectl get 命令中。

# 要打印有关 Pod 状态的信息
kubectl get pods <pod-name> --server-print=false

1.7 排序列表对象

  将对象排序后输出到终端窗口，可以将 --sort-by 参数添加到支持的 kubectl 命令。 通过使用 --sort-by 参数指定任何数字或字符串字段来对对象进行排序。 要指定字段，请使用 jsonpath 表达式。

kubectl [command] [TYPE] [NAME] --sort-by=<jsonpath_exp>

# 打印按名称排序的 Pod 列表
kubectl get pods --sort-by=.metadata.name

1.8 常用操作

  1.kubectl apply：以文件或标准输入为准应用或更新资源。

1.使用 example-service.yaml 中的定义创建服务。
  kubectl apply -f example-service.yaml

2.使用 example-controller.yaml 中的定义创建 replication controller。
  kubectl apply -f example-controller.yaml

3.使用 <directory> 路径下的任意 .yaml、.yml 或 .json 文件 创建对象。
  kubectl apply -f <directory>

  2.kubectl get - 列出一个或多个资源。

1.以纯文本输出格式列出所有 Pod。
  kubectl get pods

2.以纯文本输出格式列出所有 Pod，并包含附加信息(如节点名)。
  kubectl get pods -o wide

3.以纯文本输出格式列出具有指定名称的副本控制器。提示：你可以使用别名 'rc' 缩短和替换 'replicationcontroller' 资源类型。
  kubectl get replicationcontroller <rc-name>

4.以纯文本输出格式列出所有副本控制器和服务。
  kubectl get rc,services

5.以纯文本输出格式列出所有守护程序集，包括未初始化的守护程序集。
  kubectl get ds --include-uninitialized

6.列出在节点 server01 上运行的所有 Pod
  kubectl get pods --field-selector=spec.nodeName=server01

  3.kubectl describe - 显示一个或多个资源的详细状态，默认情况下包括未初始化的资源。

1.显示名为 <pod-name> 的 Pod 的详细信息。
  kubectl describe nodes <node-name>

2.显示名为 <pod-name> 的 Pod 的详细信息。
  kubectl describe pods/<pod-name>

3.显示由名为 <rc-name> 的副本控制器管理的所有 Pod 的详细信息。
  注明：副本控制器创建的任何 Pod 都以副本控制器的名称为前缀。
  kubectl describe pods <rc-name>

4.描述所有的 Pod
  kubectl describe pods

  kubectl get 命令通常用于检索同一资源类别的一个或多个资源。 它具有丰富的参数，允许使用 -o 或 --output 参数自定义输出格式。 可以指定 -w 或 --watch 参数以开始监测特定对象的更新。 kubectl describe 命令更侧重于描述指定资源的许多相关方面。可以调用对 API 服务器 的多个 API 调用来为用户构建视图。 例如，该 kubectl describe node 命令不仅检索有关节点的信息，还检索在其上运行的 Pod 的摘要，为节点生成的事件等。

  4.kubectl delete - 基于文件、标准输入或通过指定标签选择器、名称、资源选择器或资源来删除资源。

1.使用 pod.yaml 文件中指定的类型和名称删除 Pod。
  kubectl delete -f pod.yaml

2.删除所有带有 '<label-key>=<label-value>' 标签的 Pod 和服务。
  kubectl delete pods,services -l <label-key>=<label-value>

3.删除所有 Pod，包括未初始化的 Pod。
  kubectl delete pods --all

  5.kubectl exec - 对 Pod 中的容器执行命令。

1.从 Pod <pod-name> 中获取运行 'date' 的输出。默认情况下，输出来自第一个容器。
  kubectl exec <pod-name> -- date

2.运行输出 'date' 获取在 Pod <pod-name> 中容器 <container-name> 的输出。
  kubectl exec <pod-name> -c <container-name> -- date

3.获取一个交互 TTY 并在 Pod  <pod-name> 中运行 /bin/bash。默认情况下，输出来自第一个容器。
  kubectl exec -ti <pod-name> -- /bin/bash

  6.kubectl logs - 打印 Pod 中容器的日志。

1.返回 Pod <pod-name> 的日志快照。
  kubectl logs <pod-name>

2.从 Pod <pod-name> 开始流式传输日志。这类似于 'tail -f' Linux 命令。
  kubectl logs -f <pod-name>

  7.kubectl diff - 查看集群建议更新的差异。

1.“pod.json”中包含的差异资源。
  kubectl diff -f pod.json

2.从标准输入读取的差异文件。
  cat service.yaml | kubectl diff -f -

1.9 创建和使用插件

  1.编写和使用 kubectl 插件：

# 用任何语言创建一个简单的插件，并为生成的可执行文件命名
# 以前缀 "kubectl-" 开始
cat ./kubectl-hello
#!/bin/sh

# 这个插件打印单词 "hello world"
echo "hello world"

sudo chmod a+x ./kubectl-hello

# 并将其移动到路径中的某个位置
sudo mv ./kubectl-hello /usr/local/bin
sudo chown root:root /usr/local/bin

# 你现在已经创建并"安装了"一个 kubectl 插件。
# 你可以开始使用这个插件，从 kubectl 调用它，就像它是一个常规命令一样
kubectl hello
hello world
# 你可以"卸载"一个插件，只需从你的 $PATH 中删除它
sudo rm /usr/local/bin/kubectl-hello

  3.查看可用的所有 kubectl 插件：

kubectl plugin list

2 YAML文件

2.1 YAML文件的概念

  Kubernetes使用YAML(或JSON)文件来声明和配置其资源需求。这些文件通常被命名为.yaml并存放在本地文件系统中，或者直接通过Kubectl命令行工具在命令中指示。

YAML文件的作用如下：

  描述资源配置：YAML文件用于详细描述一个或多个Kubernetes对象(如Pods、Services、Deployments等)。

  部署资源：通过Kubectl工具应用这些配置文件，可以在Kubernetes集群中创建或更新相应的资源。

  环境抽象：YAML文件使得基础设施即代码成为可能，便于版本控制和团队协作。

2 .2 YAML文件格式

  一个YAML文件由以下内容构成。

1.大小写敏感

3 k8s的节点

  Kubernetes 节点是集群中的工作节点，负责在集群中运行容器化应用程序。每个节点可以是物理机器或虚拟机，它们执行实际的计算任务，管理容器并提供网络和存储资源。Kubernetes 节点的介绍：

  1.Kubelet：每个节点上的代理，负责与主控节点通信，确保 Pod 在节点上按照预期状态运行。Kubelet 会定期检查 Master 节点以获取 Pod 配置，并根据这些配置来创建、启动、停止和监控容器。

  2.Kube-Proxy：负责维护节点上的网络代理规则，以支持服务发现和负载均衡。创建规则，将服务 IP 地址映射到后端容器的 IP 地址，以便能够从集群内部访问服务。

  3.Container Runtime：负责在节点上运行容器，如 Docker、containerd 等。启动、停止和管理容器，确保容器在指定的 Pod 中按规范运行。

  4.Pods：K8s 中最小的可部署单元，可以包含一个或多个容器。同一个 Pod 中的容器共享相同的网络命名空间和存储卷，共享数据和进行通信。

  5.节点资源： 节点具有计算资源（CPU、内存等）和存储资源（本地存储、持久卷等），这些资源用于托管容器和满足应用程序的资源需求。

  6.节点标签和污点： 节点可以使用标签（Labels）进行分类和标识，以便进行节点选择和调度。同时，节点还可以带有污点（Taints），用于影响 Pod 被调度到节点上的条件。

  7.节点状态： Kubelet 会报告节点的状态给 Master 节点，包括节点资源利用率、健康状况和其他信息。

  8.容器网络： 节点上的容器可以通过虚拟网络进行通信。Kubernetes 提供多种容器网络插件，用于创建和管理容器之间的网络连接。

Kubernetes 节点是集群中的工作单元，它们在集群中执行容器化应用程序，并通过与 Master 节点的交互来实现自动化的容器编排和管理。

3.1 节点管理

  在 Kubernetes 中，节点管理涉及管理集群中的工作节点，确保它们的状态和资源利用率正常，以及进行节点的扩展和缩减。以下是常见的节点管理操作：

  1.查看节点状态： 使用以下命令查看集群中所有节点的状态、资源利用率和条件：

kubectl get nodes
kubectl describe node <node-name>

  2.标记节点： 使用标签（Labels）来分类和标识节点，以便将 Pod 调度到特定的节点上。可以通过编辑节点的标签来实现：

kubectl label node <node-name> <label-key>=<label-value>

  3.节点扩展和缩减： 要向集群中添加新节点或从集群中删除节点，可以根据需要调整底层的基础设施，然后 Kubernetes 会自动检测并将新的节点加入或从集群中移除。

  4.节点污点和容忍度： 节点污点（Taints）可以影响 Pod 被调度到节点上的条件。可以为节点添加污点，并为需要容忍这些污点的 Pod 添加相应的容忍度（Tolerations）。

  5.节点维护和更新： 当需要进行节点维护或更新时，可以通过将节点设置为 “维护” 状态，以通知 Kubernetes 不要在该节点上创建新的 Pod。一些工具（如 kubectl drain）可以协助运维人员优雅地将节点上的 Pod 迁移到其他节点上。

  6.节点的移除和替换： 当需要移除或替换节点时，可以使用节点驱逐（Eviction）机制，以确保在迁移 Pod 时不会造成中断。然后你可以将节点从集群中移除。

  7.自动伸缩： Kubernetes 支持自动伸缩节点的功能，根据资源使用情况和负载情况来自动扩展或缩减节点数。

  8.节点资源限制和保留： 可以在节点上设置资源限制，以确保节点上的容器不会占用过多的计算资源。同时，可以为特定的节点保留资源，以确保特定的 Pod 或服务有足够的资源。

  Kubernetes 提供了丰富的功能来管理集群中的节点，以确保集群的稳定性、可用性和性能。根据实际需求，可以使用适当的命令和工具来执行节点管理操作。

  在 Kubernetes 中，可以使用 kubectl 命令来查看节点的状态、资源利用率和条件。

1.查看所有节点状态：将显示节点的名称、状态、版本等信息。
  kubectl get nodes
  
2.查看节点详细信息：将显示有关节点的详细信息，包括资源利用率、污点、容忍度和其他条件。
  kubectl describe node <node-name>
  
3.查看节点资源利用率：将显示所有节点的资源利用率摘要，如CPU和内存的使用情况。

  通过上述命令，可以查看节点的状态、资源利用率、污点和容忍度等信息。

3.3 节点心跳

  在 Kubernetes 中，节点之间的通信是通过节点心跳（Node Heartbeat）来实现的。节点心跳是一种机制，用于检测节点的健康状态和可用性，以及在节点不可用时触发相应的处理。

  节点心跳的工作原理如下：

  1.Kubelet 心跳： 每个节点上的 Kubelet 会定期向 Master 节点发送心跳信号。这个心跳信号包含节点的状态、资源利用率和其他信息。Master 节点通过接收这些心跳信号来监控节点的健康状况。

  2.节点不可用检测： Master 节点会根据心跳信号检测节点是否处于可用状态。如果 Master 节点在一定时间内没有收到节点的心跳信号，就会认为该节点不可用。

  3.节点删除和替换： 一旦 Master 节点确认某个节点不可用，它将触发相关的处理，如将该节点上的 Pod 迁移到其他健康节点上。这有助于确保应用程序的高可用性。

  4.自动扩展和缩减： 节点心跳也是自动扩展和缩减集群节点数的依据之一。如果节点资源利用率高，而心跳信号表明有节点处于闲置状态，集群可以根据这些信息自动扩展节点数以满足需求。

  5.节点维护和更新： 当需要对节点进行维护或更新时，可以通过标记节点为“维护”状态，停止节点的心跳信号。这会通知 Master 节点在节点维护期间不要在该节点上创建新的 Pod。

  节点心跳是 Kubernetes 集群中确保节点健康、可用性和高可用性的重要机制。通过节点心跳，Kubernetes 可以自动监控和管理节点状态，以实现自动化的容器编排和管理。

查看节点心跳：

  在 Kubernetes 的节点状态信息中，心跳时间通常体现在节点的 “Conditions” 部分中的 “LastHeartbeatTime” 字段。这个字段记录了节点最近一次发送心跳信号的时间戳。

3.4 节点控制器

  在 Kubernetes 中，节点控制器（Node Controller）是集群的一个核心控制器，负责监控和维护节点的健康状态，确保集群中的节点始终处于正常运行状态。节点控制器在节点不可用时会触发自动修复机制，确保集群的可用性和稳定性。

  节点控制器的主要功能包括：

  1.节点健康检查： 节点控制器定期检查集群中所有节点的状态，包括检查节点的心跳、资源利用率和其他健康状况。

  2.节点故障检测： 当节点控制器检测到某个节点不可用（例如，没有收到心跳信号），它会将该节点标记为不可用状态。

  3.自动修复： 一旦节点被标记为不可用，节点控制器将触发自动修复机制，将受影响的 Pod 迁移到其他健康的节点上，以确保应用程序的高可用性。

  4.节点维护和替换： 当节点需要进行维护或更新时，节点控制器可以协助在节点维护期间停止在该节点上创建新的 Pod，以免影响维护操作。

  5.自动扩展和缩减： 节点控制器可以根据节点资源利用率和负载情况自动进行节点的扩展和缩减，以满足应用程序的需求。

  节点控制器是 Kubernetes 集群中负责监控和维护节点状态的重要组件之一。它确保集群中的节点始终处于可用状态，通过自动化的方式维护和修复节点，以提供高可用性的容器编排和管理。

3.5 节点与控制面的通信

  在 Kubernetes 集群中，节点（Node）和控制面（Control Plane）之间通过不同的通信渠道进行交互。控制面包括 Master 节点以及各种控制器组件，而节点是工作节点，负责运行容器化应用程序。以下是节点与控制面之间的几种通信渠道：

  1.Kubelet 与 API Server 之间的通信： Kubelet 是运行在每个节点上的代理进程，负责与 Master 节点上的 API Server 进行通信。Kubelet 定期发送心跳信号、获取 Pod 配置、报告节点状态和资源利用率等信息给 API Server。

  查看kubelet systemctl status kubelet

  2.Kube-Proxy 与 API Server 之间的通信： Kube-Proxy 负责在节点上维护网络代理规则，以支持服务发现和负载均衡。它也需要与 API Server 进行通信，以获取服务和端点的信息，并保持规则的一致性。

  查看kubeproxy kubectl get daemonsets kube-proxy -n kube-system

  3.Pod 与 API Server 之间的通信： 在应用程序中运行的 Pod 可以通过 Service（服务）来暴露自己，然后其他 Pod 或外部客户端可以通过 Service IP 地址与 Pod 进行通信。这个通信是通过 Kube-Proxy 和 API Server 协同工作实现的。

  4.Node Controller 与 API Server 之间的通信： 节点控制器负责监控和维护节点的健康状态。它会定期与 API Server 通信，以获取节点的状态信息，从而实现自动修复和自动扩展。

  5.Pod Scheduler 与 API Server 之间的通信： Pod 调度器负责将新的 Pod 调度到适当的节点上。它与 API Server 通信以获取节点和资源信息，以便做出调度决策。

  6.Controller Manager 与 API Server 之间的通信： Controller Manager 包括各种控制器，如副本控制器、服务控制器等。它们与 API Server 通信以监控和管理资源的状态。

  这些通信渠道是 Kubernetes 集群内部的关键组件，它们通过 API Server 这个核心组件来交互。API Server 提供了 RESTful API，用于各个组件之间的通信和交互，从而实现容器的自动化编排和管理。

4 k8s容器

  容器是用于运行和隔离应用程序及其依赖的轻量级虚拟化技术。容器允许将应用程序、其所需的库、配置和环境一起打包，以便在不同的环境中一致地运行。

  1.容器镜像（Container Image）：轻量级、可执行的软件包，包含了运行应用程序所需的所有代码、运行时、库和配置。容器镜像是创建容器的基础。Docker Hub 和其他容器注册表提供了大量的公共和私有容器镜像供使用。

  2.Pod： 在 Kubernetes 中，最小的可部署单元是 Pod。Pod 是一个或多个紧密耦合的容器的集合，它们共享相同的网络命名空间、存储卷和其他资源。Pod 可以用于部署多个紧密协作的容器，如一个应用程序容器和一个辅助容器。

  3.容器运行时（Container Runtime）： 容器运行时是负责在宿主机上运行和管理容器的软件组件。

  4.容器调度： Kubernetes 负责将容器调度到适当的节点上。调度器基于节点资源、亲和性、反亲和性和其他策略来确定在哪个节点上运行容器。

  5.容器生命周期管理： Kubernetes 提供了容器的生命周期管理，包括启动、停止、重启和自动修复。这有助于确保容器的可用性和健康。

  6.容器网络： Kubernetes 提供了容器之间和容器与外部网络之间的通信。每个 Pod 都有一个唯一的 IP 地址，容器可以通过 localhost 进行通信。Service 资源支持将多个 Pod 暴露给同一组 IP 和端口，从而实现服务发现和负载均衡。

  Kubernetes 借助容器技术实现了应用程序的高可用性、可伸缩性和部署自动化。容器的隔离性、轻量性和可移植性使得在 Kubernetes 中部署和管理应用程序变得更加简单和可靠。

4.1 容器镜像

  在 Kubernetes（k8s）中，容器镜像是部署应用程序的基本单元。Kubernetes 使用容器技术来封装和隔离应用程序及其所有依赖，从而实现跨环境的一致性和可移植性。

  1.容器镜像的格式：可执行的软件包，其中包含了运行应用程序所需的所有内容，如代码、运行时、库、环境变量、配置等。容器镜像采用分层文件系统的格式，允许层的共享和复用，从而减小镜像的大小。

  2.Docker 镜像格式： Kubernetes 支持多种容器运行时，但最常用的是 Docker。Docker 镜像格式是基于分层文件系统的，每一层都代表一个文件系统的更改。这种格式通过 Dockerfile 来定义容器镜像的构建过程。

  3.镜像仓库： 镜像仓库是存储和管理容器镜像的地方。常见的镜像仓库包括 Docker Hub、Google Container Registry、Amazon ECR 等。可以将自己的镜像上传到仓库，也可以从仓库中拉取现有的镜像。

  4.使用容器镜像： 在 Kubernetes 中，需要在 Pod 配置中指定要使用的容器镜像。在 Pod 的 YAML 配置文件中，可以为每个容器指定名称、镜像和其他配置选项。

apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
    - name: my-container
      image: nginx:latest

  5.多容器 Pod： Kubernetes 中的 Pod 可以包含一个或多个容器。这些容器共享同一个网络命名空间、存储卷等资源。多容器 Pod 通常用于实现应用程序的辅助任务，如日志收集、数据同步等。

  6.镜像版本和标签： 容器镜像可以有不同的版本，通常用标签来区分。在 Pod 配置中，你可以指定要使用的镜像和标签。例如，nginx:latest 中的 “latest” 是一个标签，指示使用最新版本的 nginx 镜像。

  7.私有镜像仓库： 为了安全和管理的考虑，许多组织使用私有镜像仓库存储自己的容器镜像。允许在集群中部署自己的镜像，而不必依赖公共镜像仓库。

  Kubernetes 中的容器镜像是应用程序部署的基础，通过容器化技术实现了应用程序的隔离性、可移植性和可伸缩性。

4.2 容器环境

  容器环境是指容器中运行的应用程序所处的操作系统和运行时环境。容器环境的隔离性和轻量性使得应用程序可以在不同的环境中保持一致性，并且可以在不同的节点上运行，实现了应用程序的可移植性和部署自动化。

  1.操作系统： 容器环境通常基于一个基础容器镜像，其中包含一个最小化的操作系统。这个操作系统提供了应用程序所需的运行时环境和基本库。

  2.运行时： 运行时是一个用于执行容器的软件组件，负责加载容器镜像、创建容器进程、管理容器的文件系统等。

  3.网络命名空间： Kubernetes 中的每个容器都有自己的网络命名空间，使得每个容器都有独立的网络栈。这种隔离性允许容器在同一节点上共享主机网络资源，同时保持彼此隔离。

  4.存储卷： 容器环境提供了存储卷的概念，允许容器在不同的生命周期中存储和访问数据。存储卷可以连接到宿主机上的文件系统、网络存储等，使得数据在容器之间或跨容器生命周期保持持久性。

  5.环境变量和配置： Kubernetes 允许在容器中设置环境变量，以便应用程序可以获取配置信息和运行时参数。这使得应用程序可以在不同环境中使用不同的配置。

  6.容器间通信： 在同一个 Pod 中的容器可以通过 localhost 进行通信，它们共享相同的网络命名空间。对于不同 Pod 中的容器，Kubernetes 提供了服务（Service）和网络插件来实现容器间通信。

  7.资源限制和配额： Kubernetes 允许为容器分配资源（如 CPU、内存）的限制和请求，以便更好地管理集群资源。此外，还可以设置资源配额，限制命名空间或用户可以使用的资源总量。

  容器环境使得在 Kubernetes 中部署、运行和管理应用程序变得更加高效和可靠。它们提供了一种隔离的、可移植的运行时环境，使得应用程序可以在不同的节点和环境中保持一致性。

5 k8s对象

  K8s对象是在K8s集群中用于描述和管理不同类型资源的配置。每个对象都是一个记录，包含有关资源的信息，例如副本数量、镜像、端口等。以下是常见的Kubernetes对象：

  1.Pod（Pods）： 最小的可部署对象，通常包含一个或多个容器。Pod提供了一个环境，让容器能够共享存储、网络和其他资源。

  2.ReplicaSet： 确保指定数量的Pod副本在集群中运行。当副本数量低于定义的数量时，会创建新的Pod，而当多余的Pod存在时，会将其删除。

  3.Deployment： 提供了在Pod副本之上的声明式定义，支持滚动升级和回滚。Deployment还可以在集群中维护所需的Pod数量。

  4.StatefulSet： 用于有状态应用程序，确保Pod按照特定顺序启动和停止，并提供每个Pod唯一标识和持久化存储。

  5.Service： 提供网络访问到一组Pod，可以使用Cluster IP、NodePort、LoadBalancer等类型。

  6.ConfigMap和Secret： 用于存储配置信息和敏感数据，可以将它们注入到Pod中作为环境变量或卷。

  7.DaemonSet： 用于在每个节点上运行一个Pod副本，通常用于部署一些在每个节点上执行的任务。

  8.Job和CronJob： Job用于运行一次性或有限次数的任务，而CronJob根据时间表达式定期运行任务。

  9.Namespace： 用于在集群中创建虚拟的子集群，从而隔离和分组不同的资源。

  10.PersistentVolume和PersistentVolumeClaim： 用于管理持久化存储，允许Pod使用持久性存储卷。

  这些是Kubernetes中常见的一些对象类型，每个对象都具有特定的属性和配置选项，用于定义和管理应用程序和资源。通过创建和管理这些对象，可以有效地部署、管理和扩展应用程序。要在Kubernetes集群中创建和管理这些对象，可以编写相应的YAML配置文件，并使用kubectl或其他Kubernetes API工具将其应用到集群中。

  7.CI/CD工具集成： 许多CI/CD工具（如Jenkins、GitLab CI、CircleCI等）都可以与Kubernetes集成，可以在代码提交、构建和发布过程中自动管理Kubernetes对象。

  以上是常见的Kubernetes对象管理技术。根据需求和偏好，可以选择适合您的工具和方法来有效地创建、管理和维护Kubernetes对象。

5.3 指令式命令

  Kubernetes对象管理可以通过使用kubectl命令行工具来进行指令式操作。指令式操作意味着通过命令直接告诉Kubernetes执行特定的操作，例如创建、更新、删除对象等。以下是一些常见的kubectl命令，用于指令式管理Kubernetes对象：

1.创建对象：使用`kubectl create`命令可以创建各种类型的Kubernetes对象。例如，创建一个Pod。
  kubectl create pod my-pod --image=nginx
  
2.更新对象：使用`kubectl apply`命令可以应用或更新配置文件中的对象。例如，更新一个Deployment。
  kubectl apply -f deployment.yaml
  
3.删除对象：使用`kubectl delete`命令可以删除对象。例如，删除一个Pod。
  kubectl delete pod my-pod
  
4.获取对象列表：使用`kubectl get`命令可以获取特定类型的对象列表。例如，获取所有的Pod。
  kubectl get pods

5.获取对象详细信息：使用`kubectl describe`命令可以获取特定对象的详细信息。例如，获取Pod的详细信息。
  kubectl describe pod my-pod

6.获取对象日志：使用`kubectl logs`命令可以获取Pod的日志。例如，获取Pod的日志。
  kubectl logs my-pod

7.在Pod中执行命令：使用`kubectl exec`命令可以在运行中的Pod中执行命令。例如，在Pod中执行Shell命令。

  以上是常见的kubectl指令式命令，用于管理Kubernetes对象。通过这些命令，可以直接与Kubernetes集群交互，进行对象的创建、更新、删除和监视操作。

5.4 指令式对象配置

  指令式对象配置是通过直接编写YAML或JSON格式的配置文件来定义Kubernetes对象，并使用kubectl命令行工具将这些配置文件应用到集群中。这种方式与声明式对象配置不同，声明式配置是通过kubectl apply命令来应用已经定义好的对象配置。

  以下是一个指令式对象配置的示例过程，以创建一个简单的Pod为例：

  1.创建Pod配置文件： 首先创建一个YAML文件，描述要创建的Pod的配置。例如，创建一个名为my-pod.yaml的文件：

apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
    - name: nginx-container
      image: nginx
      
      
2.使用kubectl创建：使用kubectl命令将创建好的配置文件应用到集群中，从而创建Pod。
  kubectl create -f my-pod.yaml
  
3.查看对象：使用`kubectl get`命令可以查看新创建的Pod。
  kubectl get pods
  
4.获取对象详细信息：使用`kubectl describe`命令可以获取新创建的Pod的详细信息。
  kubectl describe pod my-pod
  
5.删除对象：如果需要删除Pod，可以使用`kubectl delete`命令。
  kubectl delete pod my-pod

  这是一个指令式对象配置的基本示例过程，可以通过创建不同类型的配置文件，例如Deployment、Service、ConfigMap等，来定义和管理各种Kubernetes对象。指令式对象配置可能会导致配置漂移，因为配置文件中的状态可能与实际状态不匹配。在生产环境中推荐使用声明式对象配置和kubectl apply命令，以便更好地保持期望状态。

5.5 声明式对象配置

  在实际场景中，可以将多个Kubernetes对象的配置文件组织在一个文件夹中，以便更好地管理和组织你的应用程序的配置。以下展示如何使用配置文件夹来进行声明式管理：

  1.创建配置文件夹：创建一个文件夹，用于存放Kubernetes对象的配置文件。假设创建了一个名为my-app-configs的文件夹。

  2.在文件夹中创建配置文件： 在my-app-configs文件夹中，创建一个或多个YAML或JSON格式的配置文件，分别描述Kubernetes对象。例如，可以在该文件夹中创建一个名为deployment.yaml的文件，描述一个Deployment：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: nginx-container
          image: nginx
          
3.使用kubectl apply：`kubectl apply`命令将`my-app-configs`文件夹中的所有配置文件应用到集群中，从而创建或更新多个对象。
  kubectl apply -f my-app-configs/
  
4.查看对象：使用`kubectl get`命令可以查看已经创建的对象。
  kubectl get deployment my-deployment
  kubectl get pods -l app=my-app
  
5.更新对象：需要更新对象的配置，只需编辑配置文件，然后再次运行`kubectl apply`命令。
  kubectl apply -f my-app-configs/
  
6.回滚对象：如果更新后的状态不符合预期，可以使用`kubectl rollout undo`命令回滚到之前的版本。
  kubectl rollout undo deployment my-deployment
  
7.删除对象：如果需要删除对象，可以使用`kubectl delete`命令，也可以删除整个文件夹中的配置文件。
  kubectl delete -f my-app-configs/

5.6.2 使用Kustomize

  Kustomize 是一个开源工具，用于进行Kubernetes对象的声明式管理。允许通过自定义配置来构建和定制Kubernetes资源对象，而无需在配置文件中进行直接修改。以下是使用Kustomize进行声明式管理的示例步骤：

  1.**创建Kustomization文件：**在应用程序根目录下创建一个名为kustomization.yaml的文件，该文件描述了如何构建和定制Kubernetes对象。

  2.定义基础资源： 在kustomization.yaml中，可以定义基本的Kubernetes资源，如Deployment、Service等。例如：

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - deployment.yaml
  - service.yaml

  3.定制资源： 可以通过Patches来修改基本资源的配置。例如，可以创建一个名为patch.yaml的文件，其中包含有关如何修改基本资源的内容：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
spec:
  replicas: 5

  4.应用Kustomize： 运行kustomize build命令来应用Kustomization配置，生成最终的Kubernetes配置：

kustomize build
# 这将输出已经应用定制的配置，可以将其传递给`kubectl apply`命令。

  5.查看对象： 使用kubectl get命令可以查看已经创建的对象：

kubectl get deployment my-deployment
kubectl get service my-service

  6.更新对象： 如果需要更新对象的配置，只需编辑patch.yaml文件，然后再次运行kustomize build并传递给kubectl apply命令。

  7.删除对象： 如果需要删除对象，可以使用kubectl delete命令，同样可以应用Kustomize生成的配置。

  Kustomize允许通过定义基础资源和定制补丁，灵活地管理Kubernetes对象的配置。

6 命名空间

  Kubernetes 使用命名空间（Namespace）帮助用户在集群内创建多个虚拟集群，以便将不同的资源隔离开来。命名空间可以帮助团队、项目或应用程序在同一个 Kubernetes 集群中共享集群资源，同时保持资源的隔离。

  资源名称在命名空间内是唯一的，但不能跨命名空间。

  命名空间不能相互嵌套，每个Kubernetes资源只能在一个命名空间中。

  命名空间是在多个用户之间通过资源配额划分集群资源的一种方法。

命名空间的主要目的：

  1.隔离资源: 不同的命名空间可以容纳不同的资源，如Pod、Service、ConfigMap、Secret 等。这有助于确保资源不会意外地相互干扰。

  2.访问控制: 命名空间可以设置访问控制策略，从而限制特定用户或团队对某些命名空间中资源的访问。

  3.资源管理: 命名空间可以帮助在集群中对资源进行逻辑分组，从而更好地管理和监控资源。

  4.命名冲突避免: 不同命名空间中的资源可以使用相同的名称，因为它们的完整名称会包括命名空间作为前缀。

  要创建一个命名空间，可以使用 kubectl 命令行工具，例如：

kubectl create namespace <namespace-name>

  在创建资源时指定特定的命名空间，可以在 YAML 配置文件中的 metadata 部分添加 namespace 字段。

1.以下是一个 Pod 的简化 YAML 配置，指定它属于特定的命名空间
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
spec:
  containers:
    - name: my-container
      image: nginx
      
2.查看集群中存在的命名空间
  kubectl get namespaces

3.切换到不同的命名空间上下文
  kubectl config set-context --current --namespace=<namespace-name>

6.1 初始命名空间

  Kubernetes 启动时会创建四个初始命名空间：

  • 1.default

    Kubernetes 包含这个名字空间，以便于你无需创建新的名字空间即可开始使用新集群。

  • 2.kube-node-lease

    该名字空间包含用于与各个节点关联的 Lease（租约）对象。 节点租约允许 kubelet 发送心跳， 由此控制面能够检测到节点故障。

  • 3.kube-public

    所有的客户端（包括未经身份验证的客户端）都可以读取该名字空间。 该名字空间主要预留为集群使用，以便某些资源需要在整个集群中可见可读。 该名字空间的公共属性只是一种约定而非要求。

  • 4.kube-system

    该名字空间用于 Kubernetes 系统创建的对象。

6.2 使用命名空间

  使用命名空间（Namespace）是在 Kubernetes 中组织、隔离和管理资源的一种方法。通过使用命名空间，可以将不同的资源逻辑上分组，从而更好地管理多个应用程序、团队或项目的资源。以下是使用命名空间的一些常见场景和步骤：

  1.创建命名空间: 如果想要为特定的应用程序、团队或项目创建一个命名空间，可以使用以下命令：

kubectl create namespace <namespace-name>

  2.在命名空间中创建资源: 创建资源时，可以在资源的 YAML 配置文件中显式指定命名空间，或者使用 kubectl 命令的 --namespace 参数来指定命名空间。例如，在一个自定义的命名空间中创建一个 Deployment：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: my-namespace
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: nginx-container
          image: nginx
          
# 通过命令行创建：       
kubectl create deployment my-app --image=nginx --namespace=my-namespace

  3.查看命名空间中的资源: 可以使用以下命令来查看特定命名空间中的资源：

kubectl get pods --namespace=<namespace-name>
kubectl get services --namespace=<namespace-name>
kubectl get deployments --namespace=<namespace-name>

  4.切换命名空间上下文: 可以使用以下命令来切换当前的命名空间上下文，使得后续的命令默认在该命名空间中执行：

kubectl config set-context --current --namespace=<namespace-name>

  5.删除命名空间及其资源: 如果不再需要某个命名空间及其资源，可以使用以下命令删除它及其下属的所有资源：

kubectl delete namespace <namespace-name>

  使用命名空间可以更好地组织和隔离资源，从而在一个 Kubernetes 集群中同时管理多个应用程序、团队或项目。

  标签（Labels）是用来标识和分类资源的键值对。标签可以附加到各种 Kubernetes 资源，如 Pod、Service、Node、Deployment 等。标签本身不影响资源的运行状态，但它们可以用于进行资源选择、分组、查询和管理。

  每个标签都由一个键（Key）和一个值（Value）组成，例如：app=frontend。可以根据应用的需求自定义标签的键和值，以便更好地组织和识别资源。

  以下是使用标签的常见用途和示例：

  1.资源选择与查询: 标签可以用来选择一组资源，从而进行操作、监视或查询。

# 查找所有具有特定标签的 Pod
kubectl get pods -l app=frontend

  2.资源分组：通过为资源添加相同的标签，可以将它们逻辑上分组。

  3.资源关联：标签可以用来表示资源之间的关系。例如，将 Service 和与之关联的 Deployment 使用相同的标签，以便更容易地进行识别和管理。

  4.滚动更新和版本控制：标签可以在滚动更新时帮助你控制资源的版本。通过为不同版本的资源分配不同的标签，可以逐步更新和验证新版本的应用程序。

# Pod 配置的示例，其中添加了标签：
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  labels:
    app: frontend
    environment: production
spec:
  containers:
    - name: nginx-container
      image: nginx

  在这个示例中，app=frontend 和 environment=production 就是两个标签，用于标识 Pod 所属的应用和环境。

  Kubernetes 标签是一种非常有用的资源分类和管理工具，它可以帮助更好地组织、查询和选择资源，并在集群中实现更灵活的资源管理。

7.1 标签和命名空间

  标签（Labels）和命名空间（Namespace）在 Kubernetes 中有不同的作用和用途：

1.标签（Labels）

  • 作用：标签是用来标识和分类资源的键值对。它们通常用于在资源之间建立关联、选择、分组和管理。标签可以根据应用的需求自定义，用于表示资源的属性、用途、版本等信息。
  • 用途示例：可以使用标签来将一组相关的资源进行分组，例如将属于同一应用程序的多个 Pod 添加相同的标签。标签还可以用于资源选择、滚动更新、监视等操作。
  • 示例：一个 Pod 可以附加多个标签，例如 app=frontend 和 environment=production。

2.命名空间（Namespace）

  • 作用：命名空间是用于在 Kubernetes 集群内部创建多个虚拟集群的机制，以便将不同的资源进行隔离和组织。每个命名空间是一种逻辑分组，用于将不同应用程序、团队或项目的资源隔离开来。
  • 用途示例：命名空间可以用于在同一个 Kubernetes 集群中隔离不同应用程序的资源，从而避免资源冲突。每个命名空间内部可以包含不同的标签和资源，但它们是相互隔离的。
  • 示例：default 是 Kubernetes 默认创建的命名空间，还可以根据需要创建其他自定义的命名空间，例如 my-namespace。

3.区别总结

  • 标签用于标识、分类和关联资源，以便更好地管理和查询。
  • 命名空间用于在集群内部创建虚拟集群，将不同资源隔离和组织，以实现资源的逻辑分组和隔离。

7.2 标签选择运算符

  标签选择算符是用于在资源查询和选择时使用的操作符，它允许你基于标签的键值对进行高级筛选和匹配。以下是常见的标签选择算符：

1.等于（Equal）：使用 = 操作符来选择与指定标签键值对完全匹配的资源。
  kubectl get pods -l app=frontend

2.不等于（Not Equal）：使用 != 操作符来选择与指定标签键值对不匹配的资源。
  kubectl get pods -l app!=backend
  
3.存在（Exists）：使用 key 操作符来选择拥有指定标签键的资源，不考虑其值是否匹配。
  kubectl get pods -l environment

4.不存在（Does Not Exist）：使用 !key 操作符来选择没有指定标签键的资源。
  kubectl get pods -l !environment

5.包含（In）：使用 in 操作符来选择标签值在给定列表中的资源。
  kubectl get pods -l environment in (production, staging)

6.不包含（Not In）：使用 notin 操作符来选择标签值不在给定列表中的资源。
  kubectl get pods -l environment notin (development, testing)

7.匹配（Set）：使用 key 操作符来选择拥有指定标签键且其值不为 "" 的资源。
  kubectl get pods -l environment=

8.不匹配（Not Set）：使用 !key 操作符来选择没有指定标签键或其值为 "" 的资源。
  kubectl get pods -l !environment

  标签选择算符允许根据资源的标签进行灵活的查询和选择操作，以便更精确地管理和控制资源。可以将这些操作符与 kubectl 命令一起使用，以根据标签进行资源筛选和操作。

8 注解

  在 Kubernetes 中，注解（Annotations）是一种用来附加非标识性元数据的键值对。与标签类似，注解也可以附加到各种资源上，如 Pod、Service、Node 等。然而，与标签不同，注解不会被用于资源的选择、分组或查询，而是用来提供关于资源的附加信息和元数据。

  注解可以用于记录与资源相关的额外信息，这些信息可能对于运维、监控、日志记录、审计等方面很有用。注解的值可以是字符串，不同于标签的键和值，注解的键和值没有固定的含义，可以根据需要自定义。

  注解的用途和示例：

  1.记录信息： 注解可以用来存储关于资源的一些额外信息，如创建者、版本、说明等。

  2.指导工具行为： 有些工具或系统可能会根据资源的注解来做出不同的处理，如监控系统可能会根据特定的注解进行特殊处理。

  3.自动化任务： 注解可以用于触发自动化任务，例如在资源修改时，自动触发特定的处理脚本。

# 以下是 Pod 配置的示例，展示如何在创建 Pod 时为其添加注解
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  annotations:
    owner: john@example.com
    description: This pod is for testing purposes.
spec:
  containers:
    - name: nginx-container
      image: nginx

  在这个示例中，owner 和 description 就是两个注解，用于提供有关该 Pod 的附加信息。

1.查看资源的注解
  kubectl describe <resource-type> <resource-name>

2.查看名为 `my-pod` 的 Pod 的注解
  kubectl describe pod my-pod

9 字段选择器

  字段选择器（Field Selectors）是一种查询和选择资源的机制，允许基于资源的字段值来进行资源筛选。与标签选择器不同，字段选择器是基于资源的属性值进行筛选的，而不是基于标签的键值对。

  字段选择器可以用来进行更精确的资源选择，因为可以针对资源的特定属性进行匹配。以下是常见的字段选择器：

1.等于（Equal）：使用 = 操作符来选择字段与指定值相等的资源。
  kubectl get pods --field-selector=status.phase=Running

2.不等于（Not Equal）：使用 != 操作符来选择字段与指定值不相等的资源。
  kubectl get pods --field-selector=status.phase!=Succeeded

3.存在（Exists）：使用 key 操作符来选择拥有指定字段的资源，不考虑其值是否匹配。
  kubectl get pods --field-selector=metadata.namespace

4.不存在（Does Not Exist）：使用 !key 操作符来选择没有指定字段的资源。
  kubectl get pods --field-selector=!metadata.namespace

5.在范围内（In）：使用 in 操作符来选择字段值在给定列表中的资源。
  kubectl get pods --field-selector=metadata.name in (pod-1, pod-2)

6.不在范围内（Not In）：使用 notin 操作符来选择字段值不在给定列表中的资源。
  kubectl get pods --field-selector=metadata.name notin (pod-3, pod-4)

  字段选择器通常用于对资源的特定属性进行查询，比如选择特定状态、特定名称、特定命名空间等。可以将字段选择器与 kubectl 命令一起使用，以根据资源的字段值进行资源筛选和操作。

实例演示：

  当使用字段选择器时，可以通过 kubectl 命令的 --field-selector 参数来指定查询条件。以下的示例演示如何使用字段选择器来选择特定状态的 Pod：

1、查看所有运行中的 Pod（状态为 "Running"）：
   kubectl get pods --field-selector=status.phase=Running

2、查看所有没有成功完成的 Pod（状态不为 "Succeeded"）：
   kubectl get pods --field-selector=status.phase!=Succeeded

3、查看所有具有命名空间的 Pod：
   kubectl get pods --field-selector=metadata.namespace

4、查看所有没有命名空间的 Pod：
   kubectl get pods --field-selector=!metadata.namespace

5、查看在特定范围内的 Pod（名称为 "pod-1" 或 "pod-2"）：
   kubectl get pods --field-selector=metadata.name in (pod-1, pod-2)

6、查看不在特定范围内的 Pod（名称不为 "pod-3" 或 "pod-4"）：
   kubectl get pods --field-selector=metadata.name notin (pod-3, pod-4)

  可以根据需要使用不同的字段选择器来查询和选择特定的资源。字段选择器可以与 kubectl 支持的各种资源一起使用，如 Pod、Service、Node 等。

10 Kubernetes组件

  Kubernetes 是开源的容器编排和管理平台，由多个组件协同工作来实现容器化应用程序的部署、伸缩、管理和操作。以下是 Kubernetes 中核心组件：

  1.Kubelet：每个节点上的代理，负责与主控节点通信，确保在节点上运行的容器按照期望的状态运行。

  2.Kube-Proxy：负责维护节点上的网络代理，帮助实现服务发现和负载均衡。为服务提供了一个虚拟 IP 地址，并将请求路由到正确的容器。

  3.kube-controller-manager：管理着多个控制器，这些控制器监控系统状态的变化，并确保系统达到期望的状态。其中一些控制器包括 Replication Controller、Node Controller、Namespace Controller 等。

  4.kube-scheduler：负责将新的 Pod 分配到集群中的节点上。它根据资源需求、亲和性规则等因素选择最适合的节点。

  5.etcd：高可用的键值存储系统，用于存储 Kubernetes 集群的所有配置数据、状态信息等。

  6.API Server：集群的前端接口，用于管理集群的操作。所有的操作和管理命令都通过 API Server 进行。

  7.kube-proxy：负责维护节点上的网络代理，帮助实现服务发现和负载均衡。

  8.Container Runtime：负责运行容器的软件，如 Docker、containerd 等。它负责启动、停止和管理容器。

  9.CoreDNS 或 kube-dns：用于提供集群内部的 DNS 服务，使得可以使用服务名称来访问其他容器。

这些组件一起工作，以实现容器化应用程序的自动化管理、伸缩和部署。

  Kubernetes 中的各个组件协同工作，以实现容器化应用程序的管理和编排。以下是这些核心组件如何工作的描述：

  1. Kubelet：在每个节点上运行，并与主控节点通信。定期从主控节点获取期望的 Pod 状态，然后监控并维护节点上的容器以达到这个状态。Kubelet 还会报告容器的状态和性能指标给主控节点。
  2. Kube-Proxy： 负责在节点上维护网络代理规则，以支持 Kubernetes 服务的发现和负载均衡。它会监听 Service 和 Endpoint 的变化，并根据这些变化更新网络规则。
  3. kube-controller-manager：包含多个控制器，这些控制器负责监控集群状态的变化，并确保系统保持期望的状态。例如，Replication Controller 负责维护指定副本数量的 Pod，Node Controller 负责检测和处理节点状态变化。
  4. kube-scheduler：根据一系列的调度策略将新的 Pod 分配到合适的节点上。考虑节点的资源情况、亲和性和反亲和性规则，以及其他调度需求来做出决策。
  5. etcd：高可用的键值存储系统，用于存储 Kubernetes 集群的所有配置数据和状态信息。各个组件通过 etcd 来进行通信和共享状态信息。
  6. API Server：集群的前端接口，负责处理对集群的所有操作请求。验证和处理请求，然后将请求传递给其他组件进行处理。
  7. Container Runtime：负责运行容器，根据 Pod 配置启动、停止和管理容器。
  8. CoreDNS 或 kube-dns：负责提供集群内部的 DNS 服务，将服务名称解析为 IP 地址，以便容器之间可以通过服务名称相互通信。

  这些组件之间的通信和协作，以及它们的功能共同作用，使得 Kubernetes 可以实现容器化应用程序的自动管理、伸缩和部署。通过集成这些组件，Kubernetes 提供了一个强大的平台来简化容器化应用的部署和运维。

11 Kubernetes API

  Kubernetes API 是用于与 Kubernetes 集群交互的接口，允许用户、开发者和工具通过 HTTP 请求来管理和操作集群中的资源。Kubernetes API 提供了对集群配置、状态、操作和元数据的访问。

  Kubernetes API 可以通过多种方式访问，包括命令行工具（如 kubectl）、编程语言的客户端库（如 Python、Go、Java 等）、自定义脚本和第三方工具。通过 Kubernetes API，可以执行以下操作：

  1.创建、更新和删除资源：使用 API 创建、更新和删除 Kubernetes 中的各种资源，如 Pod、Service、Deployment 等。

  2.查询和监控资源：查询资源的状态、属性和元数据，以便了解资源的运行状态和配置。

  3.伸缩和扩展应用：使用 API 对应用进行伸缩，增加或减少实例数量，以适应流量需求。

  4.滚动更新：使用 API 对 Deployment 进行滚动更新，以更新应用程序的版本。

  5.管理集群配置：通过 API 对集群的配置进行操作，如添加命名空间、创建 RBAC 角色等。

  6.管理资源关系：使用 API 建立资源之间的关系，如 OwnerReferences，以实现资源的属主和附属关系。

  Kubernetes API 遵循 RESTful 风格，资源被表示为资源类型（例如 “pods”、”services” 等），可以通过 HTTP 方法（GET、POST、PUT、DELETE 等）对资源进行操作。每个 Kubernetes 资源都有一个唯一的 API 路径，用于对该资源进行操作。

  可以通过以下方式来访问 Kubernetes API：

  • 命令行工具：使用 kubectl 命令行工具可以方便地与 Kubernetes API 进行交互。
  • 编程语言客户端库：Kubernetes 提供了多种编程语言的客户端库，使开发者能够在自己喜欢的编程语言中使用 Kubernetes API。
  • HTTP 请求：你可以直接通过发送 HTTP 请求到 Kubernetes API Server 来访问 API。这种方式通常需要处理认证和授权。

  Kubernetes API 是构建自动化、编排和管理容器化应用的关键组成部分，它使得开发人员和运维人员能够更灵活地管理和控制 Kubernetes 集群中的资源。

13.1 CRD介绍

  K8S资源类型不止有namespace，还有很多，不过都是系统自带的，可以对k8s中的资源进行自定义。

  CRD是 Kubernetes 提供的一种机制，允许用户定义自己的资源类型，这些自定义资源可以像 Kubernetes 原生资源（如 Pod、Service、Deployment 等）一样被管理。

1.为什么需要CRD？

  扩展 Kubernetes API：K8s 的原生资源可能无法满足所有用户的需求。CRD 允许用户定义自己的资源类型，从而扩展 Kubernetes 的功能。

  管理复杂应用：有些应用可能需要管理一些特定的资源，这些资源不属于K8s原生支持的范围。通过CRD可以将这些资源纳入 Kubernetes的管理范围，实现统一的资源管理。

2.CRD的作用

  定义资源结构：CRD 允许定义资源的结构，包括其字段和数据类型。

  管理资源生命周期：Kubernetes 将为你管理这些自定义资源的生命周期，包括创建、更新、删除等操作。

  集成 K8s 生态系统：CRD 可以与 Kubernetes 的其他组件（如控制器、操作符等）集成，实现更复杂的业务逻辑。

在Kubernetes 的自定义资源定义（CRD）中，CRD 本身只定义了资源的结构和 API，但它不会直接执行任何创建、更新或删除操作。这些操作需要通过一个控制器（Controller）来实现。控制器是一个独立的程序，它监听 CRD 的变化，并根据这些变化执行实际的操作。

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  # 名字必需与下面的 spec 字段匹配，并且格式为 '<名称的复数形式>.<组名>'
  name: crontabs.stable.example.com

  # 组名称，用于 REST API：/apis/<组>/<版本>

    - name: v1

      served: true
      # 其中一个且只有一个版本必需被标记为存储版本
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                cronSpec:
                  type: string
                image:
                  type: string
                replicas:
                  type: integer
  # 可以是 Namespaced 或 Cluster
  scope: Namespaced
  names:
    # 名称的复数形式，用于 URL：/apis/<组>/<版本>/<名称的复数形式>
    plural: crontabs
    # 名称的单数形式，作为命令行使用时和显示时的别名
    singular: crontab

    kind: CronTab

    - ct

  2.在k8s-master节点创建资源清单文件

  这是一个 Kubernetes 的 ‌ReplicationController (RC)‌ 资源配置文件，文件名为 rc-nginx.yaml。它的主要作用是确保在 dean 命名空间中始终运行着 ‌3个‌ 带有 app: rc-nginx 标签的 Nginx Pod 副本。

[root@k8s-master ~]# vim rc-nginx.yaml
---
kind: ReplicationController  # 资源类型：副本控制器
apiVersion: v1    # API 版本： v1

# 元数据信息
metadata:
  name: rc-nginx-pod   # RC资源的名称，在命名空间内唯一
  namespace: dean     # RC所属的命名空间，该控制器及其管理的Pod都将部署在名为dean的命名空间中

# 核心控制逻辑
spec:
  replicas: 3   # 期望维持的Pod副本数为3
  selector:     # 标签选择器，必须匹配Pod模板中的labels
    app: rc-nginx   # 选择具有 app=rc-nginx 标签的Pod

# Pod模板：RC创建新Pod时使用此模板
  template:
    metadata:
      labels:                   # Pod的标签，必须匹配上面的selector
        app: rc-nginx
    spec:
      containers:
        - name: rc-nginx-container # 容器名称
          image: nginx:1.19  # 镜像信息，使用的镜像及版本
          imagePullPolicy: IfNotPresent   # 镜像拉取策略：本地有则用本地，没有则拉取
          ports:
            - containerPort: 80   # 容器内监听的端口

1.镜像拉取策略：

  Always：每次启动容器时，都会从镜像仓库中拉取最新的镜像。这是默认的镜像拉取策略，在配置文件中明确指定了imagePullPolicy为IfNotPresent或Never时，才会覆盖这一默认行为。

  IfNotPresent：如果节点上已经存在相同的镜像，则直接使用节点上的镜像；如果节点上没有该镜像，则从镜像仓库中拉取最新的镜像。这种策略有助于减少不必要的网络流量和镜像仓库负载，同时确保节点上已缓存的镜像得到利用。

  Never：只使用节点上已经存在的镜像，不会从镜像仓库中拉取镜像。如果节点行没有所需的镜像，则Pod启动失败，并报告错误。

2.selector：

  是 RC 与 Pod 关联的关键。RC 会查找所有标签中包含 app: rc-nginx 的 Pod。

  如果现网中已有带此标签的 Pod，RC 会接管它们。

  如果需要新建 Pod，RC 会使用下面的 template 来创建，并自动打上这些标签。

  5.扩容/缩容Pod副本

语法：kubectl scale [资源类型] [资源名称] --replicas=[数量] -n [命名空间]
1.扩容到5个副本
  # 完整写法
  kubectl scale replicationcontroller rc-nginx-pod --replicas=5 -n dean
  
  参数说明：
  kubectl scale：主命令，用于改变资源副本数。
  rc：资源类型，表示Replicationcontroller。已被Deployment缩取代，因为其支持滚动更新、回滚等。
  rc-nginx-pod：扩容的Replicationcontroller的名称。
  --replicas=5：参数，将资源副本数设置为5。
  -n dean：指定在哪个命名空间中执行。
  
  # 缩写写法
  kubectl scale rc rc-nginx-pod --replicas=5 -n dean
  
  # 使用文件
  kubectl scale --replicas=5 -f rc-nginx.yaml

2.查看扩容结果
  kubectl get pods -n dean

3.缩容到2个副本
  kubectl scale rc rc-nginx-pod --replicas=2 -n dean
